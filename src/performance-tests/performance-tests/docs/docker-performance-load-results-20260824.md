# Docker Spring 성능·부하 테스트 결과

## 1. 결론

- Docker에서 Spring과 k6를 실행한 결과, **Connection Refused, `status=0`, timeout은 3회 반복 모두 0건**이었다.
- 성능 테스트(기존 동시성 시나리오 1~5)는 3회 모두 업무 규칙과 임계값을 통과했다.
- 부하 테스트의 50 RPS baseline과 혼합 읽기·구매 테스트는 예정된 요청을 모두 실행했다.
- 500 RPS까지 증가시키는 stress와 spike에서는 완료된 HTTP 요청의 실패가 아니라 `dropped_iterations`가 발생했다. 응답이 느려져 k6의 VU 1,200개가 모두 사용되면서 예정된 요청 일부를 시작하지 못한 것이다.
- 이 부하 테스트 당시 가장 큰 애플리케이션 병목 후보는 판매 목록 조회의 N+1 쿼리였다. 판매 목록 1회에 상품 단건 조회가 약 107회 추가되어, 각 부하 테스트 회차에서 약 758만~784만 회의 상품 단건 쿼리가 실행됐다.
- 부하 테스트의 `checks`와 `load_errors` 실패에는 테스트 코드 결함이 섞여 있다. 실제 생성 데이터의 판매는 106개인데 검증 코드가 104개를 기대하므로, 정상적인 HTTP 200 목록 응답도 실패로 기록된다. 서버 용량 판정과 테스트 검증 오류를 구분해야 한다.

> 후속 작업에서 `@EntityGraph(attributePaths = "goods")`를 적용해 판매 목록 1회의 SQL을 107회에서 1회로 줄였다. [동시성 적용 전후 결과](./entitygraph-concurrency-results-20260824.md)에서 기능 회귀가 없음을 확인했고, [부하 적용 전후 결과](./entitygraph-load-results-20260824.md)에서 baseline 목록 p95 46.7%, stress drop 67.9%, 평균 DB CPU 88.4% 감소를 확인했다. 이 문서 4~5장의 원래 부하 수치는 EntityGraph 적용 전 기준값이다.


Spring과 k6가 같은 네트워크 네임스페이스를 사용하므로 k6 스크립트의 `localhost:8080`을 바꾸지 않았다. 호스트에도 `127.0.0.1:8080`을 매핑했다.

프로필별 주요 설정은 다음과 같다.

| 구분 | Spring 프로필 | Tomcat | HikariCP |
|---|---|---|---|
| 성능/동시성 | `performance,concurrency` | max threads 300, min spare 30 | max pool 40, min idle 10 |
| 부하 | `performance,load` | max connections 1,500, accept count 300, max threads 240, min spare 24 | max pool 30, min idle 10, connection timeout 5초 |

각 회차 전 기존 데이터 생성 스크립트로 PostgreSQL과 Redis를 초기화했다. 부하 테스트는 회차마다 Spring 컨테이너를 `performance,load` 프로필로 재생성했다. 테스트 중 애플리케이션과 DB 자원, PostgreSQL 연결·락·쿼리를 5초 간격으로 수집했다.

### 4.4 임계값 실패를 해석할 때의 주의점

baseline, stress, spike, mixed의 k6 프로세스 종료 코드에는 임계값 실패가 포함됐다. 그러나 서로 다른 두 문제가 함께 기록됐다.

1. **테스트 코드의 잘못된 목록 개수 검증**
   - 생성 데이터와 preflight 기준 판매 수: 106개
   - `k6/lib/workload.js`가 기대하는 판매 수: 104개
   - 따라서 정상적인 목록 HTTP 200도 `checks` 실패와 `load_errors`로 기록된다.
   - 상세 조회 ID도 1~104만 순환하여 105, 106번 판매는 부하 대상에서 빠진다.
2. **실제 용량 부족 신호**
   - stress와 spike의 `dropped_iterations`는 실제다.
   - stress와 spike의 p95도 설정 임계값을 초과했다.
   - 단, 시작된 HTTP 요청은 모두 응답했고 `http_req_failed`, timeout, Connection Refused는 0이었다.

따라서 현재 결과로 “서버 요청 실패율이 높다”고 결론 내리면 안 된다. 정확한 결론은 “고부하에서 요청을 거부하지는 않았지만, 응답 지연으로 목표 도착률을 유지하지 못했다”이다.

### 5.1 N+1 쿼리 증거

`pg_stat_statements`에서 가장 많이 실행된 쿼리는 `goods.id = ?` 상품 단건 조회였다.

| 회차 | 판매 목록 기본 쿼리 호출 | 상품 단건 쿼리 호출 | 목록 1회당 추가 상품 조회(근사) |
|---:|---:|---:|---:|
| 1 | 73,486 | 7,840,945 | 약 106.7회 |
| 2 | 71,173 | 7,593,671 | 약 106.7회 |
| 3 | 71,025 | 7,578,104 | 약 106.7회 |

`Sale.goods`는 LAZY 관계이고, `SaleServiceImpl.saleList()`가 판매 목록을 조회한 뒤 DTO 변환 중 각 판매의 `goods` 필드를 읽었다. 이 부하 테스트 당시 `SaleRepository.findAllByGoods_Status()`에는 fetch join이나 EntityGraph가 없어, 판매 목록 한 번이 판매 1회 + 상품 약 106회 쿼리로 확대됐다. 이 패턴이 CPU와 응답시간 증가의 가장 강한 원인 후보였다.

후속 단건 진단에서는 EntityGraph 적용 전 판매 목록 1회가 목록 SQL 1회와 상품 SQL 106회를 실행했고, 적용 후에는 Sale과 Goods를 함께 읽는 SQL 1회만 실행했다. 106개 응답은 그대로 유지됐다.

## 6. 개선 방안

### 우선순위 1: 테스트 검증값을 생성 데이터와 일치시킨다

- `workload.js`의 `body.length === 104`와 `% 104`를 제거한다.
- 기존 생성 데이터 JSON에서 판매 ID 목록 또는 판매 수를 읽어 검증과 상세 조회 대상을 구성한다.
- 수정 후 baseline부터 다시 실행해 `checks`, `load_errors`가 실제 서버 오류만 나타내는지 확인한다.

이 작업을 먼저 해야 이후 성능 개선 전후의 임계값 비교가 신뢰할 수 있다.

### 우선순위 2: 판매 목록 N+1을 제거한다 — 완료

- `findAllByGoods_Status()`에 `@EntityGraph(attributePaths = "goods")`를 적용했다.
- `pg_stat_statements` 기준 판매 목록 1회의 SQL이 107회에서 1회로 줄었다.
- 동시성 시나리오 1~7을 적용 전·후 각각 3회 실행해 업무 결과에 회귀가 없음을 확인했다.
- 후속 부하 테스트 3회에서 baseline 목록 p95 46.7%, stress 목록 p95 20.8%, spike 목록 p95 19.2% 감소를 확인했다.
- stress dropped iterations는 67.9%, spike는 35.5% 감소했으며 평균 App CPU는 36.6%, DB CPU는 88.4% 감소했다.
- 상세 결과는 [Sale 목록 EntityGraph 적용 전후 부하 테스트 결과](./entitygraph-load-results-20260824.md)를 참고한다.

### 우선순위 3: 안정 처리량을 별도 계단식 테스트로 찾는다

현재 stress는 여러 단계를 하나의 요약으로 합치기 때문에 어느 RPS부터 지연과 drop이 시작됐는지 정확히 알 수 없다. N+1 수정 후 250, 300, 350, 400, 450 RPS를 각각 독립적으로 2~5분 유지하고 다음 조건을 동시에 만족하는 최대값을 찾는다.

- `dropped_iterations == 0`
- `http_req_failed == 0`
- 목록·상세·구매목록 p95가 목표 이내
- CPU가 지속적으로 포화되지 않음

### 우선순위 4: Tomcat/Hikari는 쿼리 개선 후 측정 기반으로 조정한다

- Hikari active가 최대 4~5였으므로 현재 결과만으로 풀 크기를 30보다 늘릴 이유가 없다.
- 애플리케이션 CPU가 높은 상태에서 Tomcat worker를 늘리면 context switching과 지연이 더 커질 수 있다.
- N+1 제거 후 CPU, active DB connections, Tomcat busy threads를 다시 수집한 뒤 조정한다.
- k6의 `maxVUs`만 1,200보다 높이면 요청 생성은 늘릴 수 있지만 과부하를 더 키우고 실제 안정 처리량을 가릴 수 있으므로 해결책으로 사용하지 않는다.

### 우선순위 5: 장기 안정성과 환경 영향을 분리한다

- N+1과 검증 오류를 수정한 뒤 30분 soak를 실행해 heap, GC pause, 컨테이너 메모리를 함께 본다.
- 로컬 진단에는 현재 Docker 구성이 유효하지만, 최종 용량 수치는 k6와 Spring이 같은 Docker Desktop 자원을 경쟁하지 않도록 별도 PC 또는 VM에서 재검증한다.
- 비교 실험에서는 컨테이너 CPU·메모리 제한과 JVM `Xms`/`Xmx`를 고정해 회차 편차를 줄인다.

- 기존 테스트 데이터 생성 스크립트로 PostgreSQL·Redis 초기화
