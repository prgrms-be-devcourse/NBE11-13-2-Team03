# Sale 목록 EntityGraph 적용 전후 부하 테스트 결과

## 1. 최종 판단

현재 `@EntityGraph(attributePaths = "goods")` 적용은 유지하는 것이 맞다.

- 대상 관계는 컬렉션이 아니라 `Sale → Goods`의 `@ManyToOne` 단건 연관이다.
- Sale 한 건에 Goods가 최대 한 건만 조인되므로 `@OneToMany` 컬렉션 fetch join처럼 루트 행이 자식 수만큼 증가하지 않는다.
- 현재 repository 반환형은 `List<Sale>`이고 `Pageable`을 사용하지 않는다. 컬렉션 fetch join과 페이징을 함께 사용할 때 발생하는 메모리 페이징 문제도 현재 코드에는 없다.
- 목록 DTO가 항상 Goods의 이름·가격·설명·이미지를 사용하므로 Goods를 함께 읽는 것은 불필요한 eager loading이 아니다.
- SQL, p95, dropped iterations, 평균 App/DB CPU가 모두 개선됐고 동시성 시나리오 1~7에도 기능 회귀가 없었다.

## 2. 실제 트레이드오프

EntityGraph가 비용이 없는 것은 아니다.

| 항목 | 적용 전 | 적용 후 | 해석 |
|---|---:|---:|---|
| 판매 목록 1회의 SQL | 107회 | 1회 | N+1 제거 |
| 목록 기본 SQL 1회 평균 실행시간 | 약 0.306ms | 약 0.453ms | Goods 열과 조인을 포함해 단일 SQL은 약 48% 무거워짐 |
| 목록+상품 SQL 총 실행시간, 회차 평균 | 약 164.23초 | 약 36.01초 | 전체 DB 실행시간 약 78% 감소 |
| 상품 단건 SQL 호출, 회차 평균 | 7,670,907회 | 55,467회 | 약 99.3% 감소 |

적용 후 남은 상품 단건 SQL은 N+1이 아니라 부하 구성의 판매 상세 API 호출에서 발생했다. 현재 읽기 비율이 목록 50%, 상세 35%이므로 `상품 단건 호출 / 목록 호출 ≈ 0.72`는 정상 범위다.

Hibernate가 생성한 목록 SQL에는 Goods 상태 필터용 join과 EntityGraph 로딩용 join이 함께 포함된다. 둘 다 ToOne join이라 행 폭증은 없지만 중복 join 비용은 남는다. 목록이 다시 병목이 되면 동일 alias를 사용하는 명시적 JPQL `join fetch` 또는 목록 DTO projection을 비교할 수 있다. 지금은 전체 부하 지표가 크게 개선됐으므로 추가 변경의 우선순위는 낮다.

## 3. 테스트 조건

- 적용 전 3회: `docker-full-suite-20260824-3x/load/run-1..3`
- 적용 후 3회: `entitygraph-load-20260824/run-1..3`
- Docker Spring + Docker k6 + PostgreSQL + Redis
- Spring 프로필: `performance,load`
- 판매 fixture: 106개
- 각 회차: preflight → warmup 10 RPS 1분 → baseline 50 RPS 5분 → stress 최대 500 RPS → spike 50→500 RPS → mixed 읽기 50 RPS + 구매 1,000건
- soak 테스트는 제외
- 각 회차마다 Spring 컨테이너를 재생성하고 DB·Redis를 기존 생성 스크립트로 초기화

기본 `application.yaml`의 개발용 `init-data.sql`이 Docker 성능 fixture를 덮어쓰지 않도록 실험 컨테이너에만 `SPRING_SQL_INIT_MODE=never`를 지정했다. 런타임 성능 설정은 바꾸지 않았다.

`workload.js`의 판매 목록 기대 개수 104는 아직 실제 106과 다르다. 이 때문에 정상 목록도 `checks/load_errors` 임계값 실패로 기록되지만 요청 전송, HTTP 응답, p95, drop, CPU, SQL 통계에는 영향을 주지 않는다. 적용 전·후 모두 같은 k6 스크립트를 사용했다.

## 6. 지표별 결론

### SQL 호출 수

목록 한 번의 SQL이 107회에서 1회로 줄었다. N+1이 실제로 제거됐다는 직접 증거다. 적용 후 목록 호출 수가 오히려 늘었는데도 상품 단건 SQL은 약 767만 회에서 약 5.5만 회로 줄었다.

### p95

정상 부하의 목록 p95가 baseline에서 46.7%, mixed에서 48.3% 감소했다. stress와 spike에서도 약 19~21% 감소했으므로 단순 SQL 개수 개선이 실제 사용자 응답시간 감소로 이어졌다.

### Dropped iterations와 완료 요청

stress drop은 67.9%, spike drop은 35.5% 감소했고 완료 요청은 각각 3.3%, 7.8% 늘었다. 같은 최대 VU에서 서버 응답이 빨라져 k6가 더 많은 목표 요청을 시작할 수 있었다는 의미다.

### CPU

| 지표 | 적용 전 | 적용 후 | 변화 |
|---|---:|---:|---:|
| App CPU 평균 | 143.00% | 90.67% | 36.6% 감소 |
| DB CPU 평균 | 70.63% | 8.20% | 88.4% 감소 |
| App CPU 순간 최대의 회차 평균 | 439.78% | 680.81% | 순간 spike는 증가 |

평균 CPU는 크게 감소했다. 적용 후 App CPU 순간 최대가 높아진 것은 더 많은 요청을 처리하는 짧은 구간의 spike이며, 전체 효율 판단에는 평균 CPU·완료 요청·drop을 함께 보는 것이 적절하다.

### DB 연결과 락

적용 전·후 모두 DB active 최대 5, 락 대기 0, 차단 세션 0, deadlock 0이었다. Hikari 풀이나 DB lock이 병목이었다는 증거는 없으며, 개선 효과는 쿼리 호출 수 감소에서 나왔다.

### HTTP와 업무 정합성

적용 후 모든 완료 요청의 `http_req_failed`는 0%였고 Connection Refused, `status=0`, timeout, Request Failed도 0건이었다. Mixed 구매는 매회 1,000건 모두 성공했다. 성능 개선으로 업무 정합성이 훼손되지 않았다.

## 7. 남은 한계

- stress 목록 p95 평균 2.77초는 임계값 2초를 초과하고 dropped가 남는다.
- spike 목록 p95 평균 3.37초는 임계값 3초를 초과하고 dropped가 남는다.
- 500 RPS를 안정 처리한다고 결론 내릴 수 없다.
- Sale 목록은 페이징 없이 106개 전체를 반환하며 ON_SALE 판매마다 Redis 재고를 개별 조회한다. 데이터가 더 커지면 다음 병목 후보가 될 수 있다.
- 먼저 k6의 104개 고정 검증을 생성 데이터 기반으로 수정하고, 이후 250~450 RPS 독립 구간 테스트로 안정 처리량을 찾아야 한다.

## 8. 복구 상태

테스트 Spring 컨테이너를 제거했고 DB·Redis를 기준 상태로 초기화했다. 생성 JSON과 SQL은 테스트 전 백업과 동일하게 복원했다. PostgreSQL과 Redis 컨테이너만 healthy 상태로 남겼다.
