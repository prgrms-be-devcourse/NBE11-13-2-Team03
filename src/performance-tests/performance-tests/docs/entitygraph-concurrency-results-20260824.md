# Sale 목록 EntityGraph 적용 전후 동시성 테스트 결과

## 1. 결론

- `SaleRepository.findAllByGoods_Status()`에 `@EntityGraph(attributePaths = "goods")`를 적용했다.
- 판매 106개인 목록을 한 번 조회했을 때 SQL은 **107회에서 1회로 감소**했다. 응답 데이터는 106개로 동일했다.
- 적용 전과 적용 후에 동시성 시나리오 1~7을 각각 3회 실행했다. 총 42개 시나리오 실행에서 업무 검증은 모두 통과했다.
- 예상 밖 응답, Connection Refused, `status=0`, timeout은 모두 0건이었다.
- 6번 결제 승인 경쟁과 7번 결제 승인·구매 취소 경쟁도 누락하지 않고 실행했으며 DB와 Redis의 최종 일관성까지 확인했다.
- 동시성 시나리오 1~7은 판매 목록 API를 호출하지 않으므로, 이 테스트의 p95 증감을 EntityGraph의 성능 효과로 해석할 수 없다. 이 테스트가 입증하는 것은 **동시성 업무 로직의 기능 회귀가 없다는 것**이다. EntityGraph의 실제 효과는 별도 목록 SQL 진단에서 확인했다.
- 이 단계에서는 요청에 따라 부하 테스트를 제외했다. 후속으로 동일 부하 suite를 3회 실행한 결과는 [Sale 목록 EntityGraph 적용 전후 부하 테스트 결과](./entitygraph-load-results-20260824.md)에 정리했다.

## 2. 변경 내용

변경 위치:

```java
@EntityGraph(attributePaths = "goods")
List<Sale> findAllByGoods_Status(GoodsStatus goodsStatus);
```

`Sale.goods`가 LAZY 관계이므로 기존 목록 조회는 DTO 변환 중 판매마다 상품을 다시 조회했다. EntityGraph가 목록 쿼리에 `goods` 로딩을 포함시켜 DTO 변환 시 추가 상품 쿼리가 발생하지 않게 했다.

자동 테스트와 Docker 실행용 `bootJar` 빌드는 성공했다.

## 3. 실험 조건

테스트 일시: 2026-08-24  
브랜치: `test/performance`  
Spring 프로필: `performance,concurrency`  
실행 환경: Docker Spring + Docker k6 + Docker PostgreSQL + Docker Redis  
k6 주소: Spring 컨테이너와 네트워크 네임스페이스를 공유한 `http://localhost:8080`  

적용 전과 적용 후 모두 다음 순서로 3회씩 실행했다.

1. 생성 스크립트로 PostgreSQL과 Redis를 전체 기준 상태로 초기화
2. preflight 통과 확인
3. DB 상태를 이어서 시나리오 1~5 실행
4. 5번 종료 후 기준 상태 초기화
5. 6번 전용 fixture 초기화 후 결제 승인 경쟁 실행 및 DB 결제 상태 확인
6. 7번 전용 fixture 초기화 후 승인·취소 경쟁 실행 및 DB·Redis 일관성 확인

6번과 7번은 서로 다른 기존 결제 fixture를 사용하므로 각 시나리오 직전에 독립적으로 초기화했다. 기존 테스트 데이터 생성 스크립트는 수정하지 않았다.

## 4. N+1 제거 검증

PostgreSQL의 `pg_stat_statements`를 초기화한 뒤, 활성 상품과 판매가 각각 106개인지 확인하고 `GET /api/sales`를 정확히 한 번 호출했다.

| 구분 | 판매 목록 쿼리 | 상품 단건 쿼리 | 전체 SQL | 반환 판매 | 응답 크기 |
|---|---:|---:|---:|---:|---:|
| 적용 전 | 1 | 106 | 107 | 106 | 25,555 bytes |
| 적용 후 | 1회 join 조회 | 0 | 1 | 106 | 25,554 bytes |

적용 전에는 다음 형태의 상품 단건 쿼리가 106회 실행됐다.

```sql
select ... from goods where id = ?
```

적용 후에는 Sale과 Goods 열을 함께 가져오는 쿼리 한 번만 실행됐다. 응답 크기의 1 byte 차이는 동적 응답 표현 차이이며, 반환 항목 수는 106개로 동일했다.

## 5. 동시성 테스트 결과

### 5.1 업무 결과

아래 결과는 적용 전 3회와 적용 후 3회에서 매번 동일했다.

| 시나리오 | 실행 부하 | 매회 결과 | 검증 결과 |
|---|---|---|---|
| 01 재고 초과 구매 | 1,000 VU | 성공 100, 기대 거절 900, 예상 밖 0 | 재고 0, `SOLD_OUT` |
| 02 단일 행 재고 처리 | 1,000 VU | 성공 1,000, 기대 거절 0, 예상 밖 0 | 재고 0, `SOLD_OUT` |
| 03 분산 판매 | 1,000 VU | 성공 1,000, 기대 거절 0, 예상 밖 0 | 판매 100개 모두 재고 0, `SOLD_OUT` |
| 04 중복 구매 경쟁 | 50 VU | 성공 1, 기대 거절 49, 예상 밖 0 | 중복 구매 방지 |
| 05 구매 취소 경쟁 | 50 VU | 성공 1, 기대 거절 49, 예상 밖 0 | 취소·재고 일관성 유지 |

6번은 적용 전·후 6회 모두 `DONE|PERF_PAYMENT_KEY_0002`를 확인했다.

7번이 허용하는 최종 상태는 다음 두 가지다.

- 승인 승리: 구매 `PURCHASED`, 결제 `DONE`, Redis 재고 99
- 취소 승리: 구매 `CANCELED`, 결제 `CANCELED`, Redis 재고 100

이번 적용 전·후 6회에서는 모두 취소 승리 상태인 `CANCELED|CANCELED`, Redis 재고 100으로 끝났고 일관성 검증을 통과했다.

### 5.2 p95 원시 결과

단위는 ms다. 1~6번은 `business_request_duration`, 7번은 `http_req_duration`의 p95다.

| 시나리오 | 적용 전 1회 | 적용 전 2회 | 적용 전 3회 | 적용 전 평균 | 적용 후 1회 | 적용 후 2회 | 적용 후 3회 | 적용 후 평균 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 01 재고 초과 구매 | 870.72 | 777.97 | 586.42 | 745.04 | 2,728.89 | 1,419.88 | 798.99 | 1,649.25 |
| 02 단일 행 재고 처리 | 990.82 | 705.00 | 373.37 | 689.73 | 1,913.72 | 1,358.84 | 865.83 | 1,379.46 |
| 03 분산 판매 | 970.58 | 854.22 | 550.85 | 791.88 | 1,436.91 | 1,329.79 | 1,099.55 | 1,288.75 |
| 04 중복 구매 경쟁 | 27.30 | 25.95 | 22.92 | 25.39 | 58.83 | 53.65 | 29.14 | 47.21 |
| 05 구매 취소 경쟁 | 196.49 | 79.00 | 76.94 | 117.48 | 208.66 | 140.14 | 95.20 | 148.00 |
| 06 결제 승인 경쟁 | 269.49 | 103.35 | 102.89 | 158.58 | 347.98 | 240.33 | 125.77 | 238.03 |
| 07 승인·취소 경쟁 | 14.65 | 9.02 | 9.75 | 11.14 | 16.94 | 12.69 | 17.01 | 15.55 |

적용 후 p95가 전반적으로 높지만 EntityGraph 때문에 느려졌다는 뜻은 아니다.

- 시나리오 1~7의 측정 요청은 구매, 취소, 결제 승인, 판매 단건 검증이며 `findAllByGoods_Status()`를 호출하지 않는다.
- 적용 전 측정은 컨테이너가 여러 사전 실행을 거쳐 충분히 예열된 뒤 수집됐고, 적용 후 첫 회차는 새 JAR로 컨테이너를 다시 기동한 직후라 JVM JIT와 연결 예열 영향이 더 컸다.
- 적용 후에도 회차가 진행될수록 1~6번 p95가 지속적으로 낮아지는 예열 패턴이 보인다.
- 따라서 이 표는 기능 회귀 확인과 실행 투명성을 위한 원시 결과이며, EntityGraph의 성능 판정 자료는 107회→1회의 SQL 비교다.

EntityGraph의 사용자 체감 응답시간 효과는 후속 부하 테스트에서 같은 warmup과 도착률 조건으로 평가했다. baseline 목록 p95는 46.7%, stress는 20.8%, spike는 19.2% 감소했다.

시나리오 1, 4, 5, 6의 높은 `http_req_failed`는 기대한 4xx 업무 거절을 포함한 값이다. 7번의 `http_req_failed=50%`도 경쟁에서 발생한 409 한 건을 k6 HTTP 기본 분류가 실패로 센 값이며, 시나리오 check와 최종 상태는 정상이다.

## 6. 판단과 후속 작업

이번 변경은 유지할 가치가 있다.

- 목록 응답 데이터와 업무 결과를 바꾸지 않았다.
- N+1 SQL을 제거했다.
- 기존 동시성·결제 경쟁 시나리오 1~7에 기능 회귀가 없었다.

다음 우선순위는 다음과 같다.

1. `workload.js`의 판매 개수 104 고정값을 실제 생성 데이터 106개와 일치시키거나 동적으로 읽게 수정
2. 판매 목록을 포함한 baseline/stress/spike 부하 테스트 3회 재실행 — 완료
3. 목록 p95, 애플리케이션 CPU, `pg_stat_statements` 호출 수 비교 — 완료
