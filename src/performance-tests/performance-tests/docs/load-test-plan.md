# Gudit 부하테스트 계획

## 1. 목적

이번 부하테스트는 기능 정합성만 확인하는 동시성 테스트와 달리 다음 질문에 답하는 것을 목적으로 한다.

1. 정상 예상 트래픽에서 응답시간과 오류율이 목표를 만족하는가?
2. 처리 한계는 초당 몇 요청에서 나타나는가?
3. 갑작스러운 트래픽 증가 후 정상 수준으로 회복하는가?
4. 장시간 실행 시 JVM, DB 연결, 메모리 사용량이 계속 증가하지 않는가?
5. 조회 트래픽과 구매 트래픽이 섞였을 때 비관적 잠금이 조회 API까지 지연시키는가?

## 2. 고정 조건

- Spring 애플리케이션은 `performance,load` 프로필로 실행한다. datasource, Redis, JWT는
  `application-performance.yaml`을 사용하고 Tomcat/Hikari 차이만 `application-load.yaml`에서
  추가 적용한다.
- 격리된 성능테스트 DB를 사용한다.
- 테스트마다 동일한 `performance-test-data.json`을 다시 적재한다.
- Spring 실행 옵션, JVM 힙, HikariCP 설정, PostgreSQL 설정을 결과와 함께 기록한다.
- k6 실행 호스트와 애플리케이션 호스트가 같다면 k6의 CPU 사용량이 결과에 영향을 줄 수 있으므로 함께 기록한다.
- 최초 1회 결과는 워밍업 결과로 취급하고 기준 결과에서 제외한다.
- 각 측정 단계 사이에 기본 15초의 회복 시간을 둔다.

## 3. API 비율

| API | 비율 | 선정 이유 |
|---|---:|---|
| `GET /api/sales` | 50% | 104개 판매와 연관 상품을 조회하는 가장 무거운 읽기 후보 |
| `GET /api/sales/{saleId}` | 35% | 일반적인 상품 상세 탐색 |
| `GET /api/purchases` | 15% | 인증 및 사용자별 조회 비용 포함 |

현재 판매 목록 구현은 `findAll()` 결과에서 연관 상품을 접근하므로 N+1 쿼리 여부를 서버 로그나 SQL 통계에서 함께 확인한다.

## 4. 실행 단계

| 순서 | 단계 | 기본 부하 | 목적 |
|---:|---|---|---|
| 0 | DB 초기화 및 preflight | 판매 104건 전수 확인 | 데이터와 JWT가 유효한지 검증 |
| 1 | 워밍업 | 10 RPS, 1분 | JIT, 커넥션 풀, Hibernate 초기 비용 제거 |
| 2 | 기준 부하 | 50 RPS, 5분 | 정상 트래픽 기준선 확보 |
| 3 | 스트레스 | 25→500 RPS, 8분 | 포화 지점과 dropped iteration 발생 지점 확인 |
| 4 | 스파이크 | 50→500 RPS 급증 | 급증 대응과 정상 부하 복귀 확인 |
| 5 | 소크 | 100 RPS, 30분 | 메모리·연결·응답시간 증가 추세 확인 |
| 6 | 혼합 구매 피크 | 읽기 50 RPS + 구매 총 1,000건(기본 동시 100 VU) | 비관적 잠금 중 조회 성능과 구매 성공률 확인 |

혼합 구매 피크는 판매 ID 2의 데이터를 소비하므로 항상 마지막에 실행한다.
구매 요청은 `shared-iterations`로 총 1,000건을 유지하며 `PURCHASE_VUS`만 조정한다. 기본 100 VU는
시작값이고, `vu-capacity-verdict.json`에서 확인한 마지막 정상 VU보다 높게 설정하지 않는다.

## 5. 초기 합격 기준

초기 기준은 실제 운영 SLO가 정해지기 전의 측정용 기준이며 첫 결과를 바탕으로 조정한다.

- 기준 부하: 오류율 1% 미만, 판매 목록 p95 1초 미만, 판매 상세 p95 500ms 미만
- 스트레스: 오류율 1% 미만, dropped iteration 0건, 판매 목록 p95 2초 미만
- 스파이크: 오류율 5% 미만, 판매 목록 p95 3초 미만, 회복 구간에서 오류 지속 없음
- 소크: 오류율 1% 미만, 판매 목록 p95 1.5초 미만, 메모리·DB 연결의 지속 증가 없음
- 혼합 구매: 구매 1,000건 성공, 재고 0, 초과 판매 없음, 구매 p95 5초 미만

## 6. 수집 항목

- k6: RPS, p50/p90/p95/p99, 최대 응답시간, 오류율, dropped iterations, VU 수
- Spring/JVM: 프로세스 CPU, heap, GC pause, thread 수, Hikari active/pending connection
- PostgreSQL: CPU, 메모리, active connection, wait event, lock 대기, slow query
- 기능 상태: 판매별 최종 재고, 판매 상태, 구매 성공 건수

프로젝트에 Actuator가 없으므로 현재 제공한 모니터는 PostgreSQL 컨테이너와 선택적 애플리케이션 컨테이너 자원을 수집한다. IntelliJ로 직접 실행하는 Spring JVM은 IntelliJ Profiler 또는 VisualVM을 함께 사용한다.

## 7. 결과 분석 및 반복

1. 기준 부하와 분산 조회의 p95를 기준선으로 저장한다.
2. 스트레스 결과에서 오류 또는 dropped iteration이 처음 발생한 RPS를 처리 한계로 기록한다.
3. DB 연결 대기와 JVM CPU 중 어느 자원이 먼저 포화되는지 대조한다.
4. 쿼리, 인덱스, 커넥션 풀 또는 잠금 범위를 조정한 후 동일 데이터와 동일 옵션으로 재실행한다.
5. 변경 전후 p95, 오류율, 최대 안정 RPS를 비교한다.
