# Tomcat accept-count별 Connection Refused 실험 결과

## 결론

`server.tomcat.accept-count`를 100에서 300, 1000으로 늘리자 5회 누적 Connection Refused는
각각 1,736건, 1,245건, 865건으로 감소했다. 100 대비 감소율은 300에서 28.3%, 1000에서
50.2%다. 따라서 이 환경에서는 `accept-count` 증가가 연결 거부를 줄이는 실질적인 효과를
보였다.

다만 반복별 편차가 매우 크고, 실행 5회를 표본 단위로 한 정확 순열 검정 결과는 모두
`p > 0.05`였다. 이번 결과만으로 "accept-count 증가가 항상 또는 통계적으로 유의하게 연결
거부를 줄인다"고 단정할 수는 없다. `accept-count=1000`에서도 한 실행은 401건이 거부되었다.

또한 거부가 줄어든 대신 평균 p95는 924ms에서 1,152ms로 증가했다. 연결을 즉시 거부하지
않고 큐에서 더 오래 기다리게 한 효과가 포함된 것으로 해석해야 한다.

## 목적

Windows 로컬 환경에서 VU 1,000이 동시에 새 연결을 만들 때, Tomcat의
`server.tomcat.accept-count`를 늘리면 서버 애플리케이션에 도달하지 못하고
`Connection Refused`가 되는 요청이 줄어드는지 확인한다.

## 실행 환경과 고정 조건

- 실행 일시: 2026-08-24
- Git 브랜치: `test/performance`
- 운영체제: Windows, k6와 애플리케이션을 같은 PC에서 실행
- k6: v2.2.0 windows/amd64
- Java: Oracle JDK 25.0.3
- Spring 애플리케이션: 호스트 JVM에서 반복마다 새로 기동 및 종료
- PostgreSQL/Redis: Docker 컨테이너
- VU: 1,000
- 부하 방식: burst, VU당 GET 요청 1회
- 연결 재사용: 사용하지 않음(`noConnectionReuse=true`)
- Tomcat: `max-threads=300`, `min-spare-threads=30`, `max-connections=8192`
- HikariCP: `maximum-pool-size=40`, `minimum-idle=10`, `connection-timeout=5000ms`
- 변경 변수: `server.tomcat.accept-count=100/300/1000`
- 반복 횟수: 조건별 5회, 총 15회

DB 작업이 없는 조회 요청을 사용했기 때문에 HikariCP와 DB Lock 영향은 최소화했다. 각 반복의
preflight는 321개 check가 모두 성공했다.

## 데이터 초기화

각 반복의 측정 전과 측정 후에 기존 `test-data/prepare-db.ps1`을 호출해 PostgreSQL과 Redis
fixture를 같은 상태로 복구했다. 기존 테스트 데이터 생성 스크립트는 수정하지 않았다. 실험
종료 후에도 동일한 초기화가 완료되었다.

## 실행 방법

프로젝트 루트에서 다음 명령을 실행한다.

```powershell
.\src\performance-tests\performance-tests\scripts\run-accept-count-experiment.ps1 `
  -ResetPerformanceDatabase `
  -RepeatCount 5 `
  -CooldownSeconds 10
```

전용 실행기는 다음을 보장한다.

1. `tomcat-accept` 그룹만 선택한다.
2. 각 조건을 정확히 5회 실행한다.
3. 반복마다 DB/Redis 초기화, Spring 기동, preflight, k6 측정, Spring 종료, 최종 초기화를 수행한다.
4. 각 실행 결과와 전체 비교 CSV를 남긴다.

모두 TCP 연결 거부로 설명된다.

| accept-count | 성공/도달 | Connection Refused | 누적 거부율 | 1회 평균 | 중앙값 | 표준편차 | 범위 | 평균 p95(ms) | 평균 http_req_failed |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 3,264 | 1,736 | 34.72% | 347.2 | 369 | 117.0 | 192~498 | 924.260 | 34.6% |
| 300 | 3,755 | 1,245 | 24.90% | 249.0 | 222 | 323.1 | 0~790 | 1,012.802 | 24.8% |
| 1000 | 4,135 | 865 | 17.30% | 173.0 | 125 | 188.2 | 0~401 | 1,152.403 | 17.2% |

`http_req_failed`는 setup/teardown의 정상 control 요청 4건도 분모에 포함하므로, 측정 요청만을
분모로 한 Connection Refused 비율보다 약간 낮다.

## 효과 크기와 통계 해석

| 비교 | 1회 평균 거부 감소 | 상대 감소율 | 정확 순열 검정 p-value |
|---|---:|---:|---:|
| 100 → 300 | 98.2건 | 28.3% | 0.5635 |
| 100 → 1000 | 174.2건 | 50.2% | 0.1190 |
| 300 → 1000 | 76.0건 | 30.5% | 0.7460 |

누적값과 평균은 accept-count가 커질수록 개선되는 방향이지만, 반복 단위 변동이 효과 크기보다
크다. 조건별 표본이 5개뿐인 현재 검정에서는 유의수준 0.05를 만족하지 못했다. 요청 5,000건을
서로 독립인 표본으로 간주하면 실행 단위의 공통 환경 영향을 무시하게 되므로 그렇게 검정하지
않았다.

## 해석과 후속 조치

1. 로컬 실험 설정으로는 `accept-count=1000`이 세 조건 중 누적 Connection Refused가 가장
   적었다. 연결 거부 감소가 우선이면 다음 상세 실험의 기준값으로 사용할 수 있다.
2. 거부 감소와 함께 p95가 증가했으므로, 단순히 성공률만 보지 말고 허용 가능한 대기 시간과
   함께 결정해야 한다.
3. `accept-count=1000`도 거부를 보장해서 제거하지 못한다. 같은 Windows PC에서 k6와 JVM이
   CPU, 스케줄링, TCP/IP 스택을 공유하는 영향이 남아 있다.
4. 통계적 결론이 필요하면 조건 실행 순서를 라운드 로빈 또는 무작위로 섞고, 조건별 반복을
   20회 이상으로 늘린 후 같은 분석을 다시 수행한다.
5. 운영 설정 채택 여부는 k6와 애플리케이션을 분리한 환경에서도 재검증한다.
